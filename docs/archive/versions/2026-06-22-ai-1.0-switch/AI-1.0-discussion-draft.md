# YayaMind AI 1.0 讨论草稿

## 文档边界

- 本文档用于承接 1.0 规划讨论中的阶段性结论。
- 当前不替代根目录 `PRD.md` / `SDD.md` / `TODO.md`。
- 有明确价值但尚未定稿的想法先放在这里，避免长期只留在聊天上下文里。
- 等 1.0 范围确认后，再统一同步到正式 PRD / SDD / TODO。

## 已确认的产品感受优先级

### 1.0 第一感受

用户希望 AI 1.0 的第一感受更偏向：

> 终于能顺畅地听我说完一大段。

这意味着 1.0 的前置体验重心应先放在语音会话稳定性，而不是一上来强调复杂自动排程。

### 对应产品判断

- 当前交互边界是手动会话边界：单击一次表示开始输入，再单击一次表示输入完毕并输出给小猫。
- 1.0 不需要把停顿、然后、等一下等词作为结束判断；用户是否说完由第二次单击决定。
- 实时转写阶段只承接和展示用户原话，不提前追问、不提前提交。
- 第二次单击后，系统才进入文本整理、理解、规划或追问。
- 语音链路要让用户感到“我可以放心说一整段，直到我自己点结束”，而不是“系统在中途替我判断说完了”。

## 暂定讨论方向

1. 先聊清楚“顺畅听完一大段”的体验标准。
2. 再决定它如何连接 `plan_day` 今日规划草稿。
3. 最后再判断哪些内容进入正式 AI 1.0 PRD / SDD / TODO。

## 已确认的 1.0 交互规则

### 语音结束后的反馈顺序

- 用户第二次单击结束输入后，小猫先展示原文确认：`我听到的是...`。
- 如果文本有明显错字、漏字或语音转写错误，系统可以直接轻量修正，不要求每次展示原文和修正版对照。
- 原文确认后进入短暂的 `文本整理中` / `理解中` / `处理中` 状态，让链路看起来稳定。
- 文本整理和理解阶段不能写入正式日程；只有明确进入直接写入或用户确认草稿后才落库。

### 复杂输入的拆解目标

- 1.0 第一版应支持一段话里同时拆出日程、待办、提醒。
- 对复杂、模糊、需要系统自动安排的输入，优先生成今日规划草稿。
- 草稿先作为预览进入日程视图，用户确认后才真正排进去；用户取消时撤销整组草稿内容。
- 如果用户说的是简单明确事项，例如“今晚七点吃饭”，可以直接安排，不强制生成草稿。

### 整组草稿和跨模块展示

- 今日规划草稿是一次语音输入生成的整组草稿，不是单个日程块。
- 日程类草稿直接投影到日程视图中，位置和时长按推断结果进入真实时间轴。
- 待办、提醒也和日程一样进入各自功能区域：待办进入待办视图 / 项目或未归类区域，提醒进入提醒相关位置。
- 用户说完一大段后，可以切到日程、待办等导航里检查本次草稿产生的内容。
- 草稿内容必须和已确认内容视觉区分，尤其是颜色或状态标识要明确表达“待确认”。
- 整组草稿的控制不放在每个卡片里，而是放在小猫对话框里。
- 小猫对话框提供三个全局操作：`确认全部`、`修改`、`取消`。
- `确认全部` 后，整组草稿转成正式日程 / 待办 / 提醒。
- `取消` 后，撤销本次草稿生成的全部内容，不保留痕迹。
- `修改` 后，重新进入语音转文字，让用户用自然语言说明要改哪些内容。
- 用户可能会先自然语言修改几轮，确认后再手动微调个别细节。
- 1.0 的核心卖点应突出“结合用户画像生成整组安排草稿”，而不是只做语音输入或普通日历新增。

### 画像与默认推断

- 画像不是只记录固定作息，而是从用户历史安排里沉淀“标题词表 + 常见时间 + 常见时长 + 用户可修改的偏好”。
- 所有用户用过的总结标题都可以归档到画像或词表中，例如“健身”“睡觉”“面试准备”等。
- 标题词表用于统一表达：用户说“健个身”“运动一下”时，如果历史里稳定使用“健身”，后续标题优先统一成“健身”，避免每次生成陌生标题。
- 画像应像一个可检索的本地记忆库，后续语音理解、query rewrite、今日规划都先查画像 / 词表。
- 优先进入 1.0 的画像字段：健身时间、睡觉时间、专注块长度、任务常见耗时。
- 画像主要从历史安排中慢慢总结，不要求用户一开始手动填写或确认。
- 画像页可以显示系统总结出的内容，用户可以手动修改，也可以通过小猫用自然语言修改。
- 当输入需要推断时间，例如“今晚要健身”，优先根据画像推断；有画像就直接读画像生成草稿。
- 如果画像不足，回到 MVP 式追问，例如“今晚几点健身”；不要凭空装懂。
- 对需要画像但没有画像的事项，系统通过本次问答和后续执行结果逐步学习。
- 草稿里可以用很轻的小图标或小标识说明“这个时间来自画像 / 历史习惯”，但不能影响整体阅读。
- 画像更新不应在每次写入时立刻完成；应在当天结束后或事项时间过去后，再根据最终事实做总结。
- 例如系统初始默认“健身 14:00-15:00”，用户手动调过后，最终以时间段过去后的真实结果作为画像学习依据。
- 对吃饭、健身等时间不稳定的事项，画像可以取中位数、最高频时间或趋势变化；如果 18:30 的频率逐渐高于 18:00，之后再逐步切换。
- “今天想轻松一点”这类心情 / 当日状态排程先不进入 1.0，后续再考虑。

### 小猫作为全局修改入口

- 小猫应成为个人助手的总入口，而不只是新增日程入口。
- 用户可以通过小猫修改任意功能区里的内容，例如工作待办删除、整个项目删除、某条待办修改、画像信息调整、休息时间修改。
- 用户说“我最近睡觉时间改了，每天几点睡几点起”，小猫应理解为画像 / 作息修改，而不是普通日程。
- 手动设置入口仍然保留，但 1.0 应让用户感到“我跟小猫说一声，它就能帮我改”。
- 自然语言修改需要经过理解和风险判断；涉及删除整个项目等高影响操作时，仍应有确认，不应静默执行。

### 全局修改的风险边界

- 删除单条工作待办 / 项目待办时需要确认；确认直接显示在小猫对话框里。
- 删除确认只展示前几行关键信息即可，例如“你要删除的是这一条吗”，避免弹出复杂表单。
- 删除整个项目属于高影响操作，必须确认，并说明项目内待办将如何处理。
- 明确的画像 / 作息修改可以直接执行，不需要反复确认。例如用户明确说“把画像里的睡觉时间改成 0:00-8:00”，系统直接修改。
- 如果用户想撤回或调整画像，可以再次通过小猫说明，或走手动设置入口。
- 当自然语言修改匹配到多个候选，例如“改那个面试”但当天有多个面试，系统必须列出候选让用户选择。
- 对“往后挪一点”这类模糊修改，不默认挪 30 分钟，应追问“挪到几点”。
- 1.0 应支持批量操作；核心不是限制数量，而是把匹配范围、影响结果和确认逻辑设计清楚。
- 批量操作可以包括批量删除、批量改时间、批量改项目归属、批量挪到明天等。
- 批量操作必须先转成可确认的候选清单，让用户知道将影响哪些事项。
- 批量操作候选清单不放在小猫气泡里，而是在主工作台右侧展示；小猫负责说明当前等待用户确认。
- 批量操作确认后按同一套单项操作规则逐条执行，并给出整体成功 / 部分失败反馈。
- 批量操作结果反馈要简短：成功的直接落入对应功能区；失败时只告诉用户失败的是哪些以及原因。
- 批量操作不作为单独复杂功能心智，而是“小猫全局修改入口”的自然延伸。

### 画像总结与后台补做

- 画像总结应在第二天首次打开时自动进行，而不是依赖用户手动点击。
- 如果系统能根据用户睡觉 / 起床画像判断一天结束，也可以在对应时机之后开始总结。
- 如果当天应用没有打开，也应在下次启动或后台可运行时补做缺失日期的画像总结。
- 画像总结依据应尽量使用最终事实，例如事项实际保留的时间、用户手动调整后的结果、已完成 / 未完成状态。
- 不要把每次初始写入都立即当作画像学习依据，避免草稿或临时安排污染画像。

### 习惯与周期安排

- 习惯 / 周期安排纳入 1.0，不单独推到 1.1。
- 示例包括“每天刷牙”“每周六下午三点上课”“每晚睡前整理明天东西”。
- 习惯 / 周期安排需要和画像、提醒、日程实例区分：有明确时间的周期事项生成日程实例，无明确时间的习惯更像待办或提醒。
- 该能力开发成本较高，应排在 1.0 后段；先完成 AI 总入口、草稿闭环、全局修改和画像基础后再做。

### 多轮上下文管理

- 1.0 必须设计多轮上下文规则，否则新增、修改、追问、画像修改、批量操作和草稿修改会互相串线。
- 小猫每轮对话都应有一个明确的当前会话状态，例如：空闲、听写中、理解中、等待补充、等待确认、展示候选、执行中、完成。
- 用户的新一句话进入时，系统先判断它是在回答上一轮问题，还是开启一个新意图。
- 如果上一轮正在等待确认 / 选择 / 补充，而用户突然说了明显无关的新任务，系统应识别为可能切换任务，先保留旧上下文，再处理新输入。
- 新输入不能被浪费。例如小猫正在等用户确认草稿时，用户说“明天三点还有个会”，系统应记住“明天三点会”这个新意图，同时询问“要先取消还是保留刚才的草稿？”
- 未确认草稿不能因为用户打断、切换页面、关闭应用而丢失，应保留到用户确认、取消或明确丢弃。
- 候选选择上下文应保留到用户取消或完成；如果用户临时切到另一个话题，新话题先处理，旧候选仍可在之后继续回来处理。
- 追问只绑定当前任务，例如“挪到几点”只应该等待时间补充；用户回答“明天还要开会”时，不能误当成挪动时间。
- 草稿修改多轮对话应始终绑定当前草稿，直到用户确认全部、取消或明确开始新任务。
- 批量操作候选清单也应有会话绑定；用户确认前不能把候选清单当成已执行结果。
- 画像 / 作息修改如果用户表达明确，可以直接执行并结束该会话；如果表达不完整，再进入等待补充。
- 小猫需要在对话框里明确当前等待用户做什么，例如“我在等你确认这组草稿”“你想把它挪到几点”“这些候选里选哪一条”。
- 用户回答“算了”时，只取消本次修改 / 追问，不影响原日程或已经确认的数据。
- 如果会话超时或用户离开，系统应保留安全状态：未确认的草稿和批量操作不落库但可恢复，已明确执行的修改保留。

### 冲突展示与处理

- 冲突不应该中途拦截整段输入；应先尽量生成完整草稿或完成安排。
- 对简单明确事项，即使与已有日程冲突，也可以安排进去，并由小猫提醒“已安排，但有冲突，可以检查一下”。
- 冲突日程在时间轴上应并排显示，而不是互相覆盖。
- 并排显示时，同一时间段的多个日程自动分列，不需要用户点击展开冲突。
- 草稿和正式日程冲突时也并排显示；草稿仍保持草稿色，正式日程保持正式状态。
- 拖动并排中的某一个日程时，只移动被拖动的那个，不一起移动其他冲突日程。
- 1.0 不设计多选移动。
- 如果被拖动的日程离开冲突时段，冲突布局应动态恢复，相关卡片回到普通宽度。

### 追问原则

- AI 没理解时可以追问一句。
- 追问应该少而准，避免连续追问造成打断。
- 对用户可直接决定的产品体验问题可以继续讨论；不要把接口、数据层等过于工程化的问题直接丢给用户决策。

## 当前需要继续讨论的问题池

- 功能范围：1.0 第一轮到底只做语音长输入，还是同时包含今日规划草稿、历史实体词表、画像参与排程。
- 页面流程：第二次单击结束后，小猫应该直接给结果、先展示理解卡片，还是进入一个可编辑草稿。
- 兜底策略：AI 没理解、听写缺字、识别出多种可能、草稿有冲突时，应该怎么问得最少。
- SDD 边界：哪些能力先走现有 `/api/input/parse` 和 `/api/input/commit`，哪些需要新增中间层或新数据结构。
- 高级场景：一段话里同时包含日程、待办、提醒、习惯、修改已有事项时，第一版处理到什么程度。

## 1.0 收口范围草案

### 1.0 不再新增的大方向

当前 1.0 范围已足够完整，后续不再主动新增大功能。新想法默认先判断是否补强以下主线；否则放 Later。

### 1.0 核心定位

YayaMind AI 1.0 是以小猫为总入口的 AI 个人执行助手。核心不是普通语音录入，而是：

```text
用户说一大段
-> 小猫听完并确认原文
-> 结合画像 / 词表 / 历史上下文理解
-> 生成整组草稿或执行明确修改
-> 用户确认 / 修改 / 取消
-> 写入日程、待办、提醒、画像、习惯等本地数据
```

### 建议开发分期

1. P0-A 会话状态机和多轮上下文。
2. P0-B 长语音输入、原文确认、文本整理和整组草稿。
3. P0-C 草稿跨模块展示和确认 / 修改 / 取消。
4. P0-D 小猫全局修改入口：单项修改、删除确认、多候选选择、画像 / 作息明确修改。
5. P0-E 批量操作：右侧候选清单、确认执行、部分失败反馈。
6. P1-A 画像与标题词表：标题归一、常见时间 / 时长、画像来源标识、第二天首次打开总结、缺失补做。
7. P1-B 习惯与周期安排：每天 / 每周规则、实例生成和后续修改。
