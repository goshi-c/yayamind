# 02 输入解析 SDD

## 目标

输入解析负责把用户对小猫说的一句话，转换成系统能处理的结构化意图。

第一版目标不是做到完美理解，而是跑通核心链路：

```text
文字/语音输入 -> 用户确认文本 -> 识别意图 -> 提取关键信息 -> 判断是否需要确认 -> 写入本地数据
```

## 输入来源

第一版支持两类输入：

- `text`：用户直接输入文字。
- `voice`：浏览器语音识别得到文本后，先让用户确认或修改，再提交解析。

语音输入不直接写入业务数据，必须先转成可确认文本。

## 第一版意图类型

### add_event

添加日程或明确时间块。

例子：

```text
明天上午 10 点开项目沟通会
今天 20:00-22:00 写方案
周六下午去训练
```

输出目标：

- 写入 `events.jsonl`。
- 如果是任务时间块，可以关联 `tasks.jsonl`。

### add_task

添加待办任务。

例子：

```text
今晚我要写完产品方案
明天记得整理作品集
这周要完成个人助手原型
```

输出目标：

- 写入 `tasks.jsonl`。
- 如果包含明确截止时间，写入 `dueAt`。

### start_work

开始执行某个任务。

例子：

```text
开始写产品方案
我现在开始做个人助手 SDD
开始工作
```

输出目标：

- 更新当前页面状态为 `working`。
- 写入 `work_logs.jsonl`。
- 如果能匹配已有任务，关联 `taskId`。

### pause_work

暂停当前工作。

例子：

```text
暂停一下
我去吃饭
先停一下
```

输出目标：

- 更新当前页面状态为 `paused`。
- 写入 `work_logs.jsonl`。

### resume_work

继续当前工作。

例子：

```text
继续刚才的任务
我回来了，继续写
继续工作
```

输出目标：

- 更新当前页面状态为 `working`。
- 写入 `work_logs.jsonl`。

### finish_work

结束当前工作。

例子：

```text
写完了
这个任务结束
今天先做到这里
```

输出目标：

- 写入 `work_logs.jsonl`。
- 更新任务或时间块状态。
- 如果没有完成，进入复盘流程。

### progress_update

记录进度或风险。

例子：

```text
我写了一半
可能今晚写不完
这个比我想的复杂
```

输出目标：

- 写入 `work_logs.jsonl`。
- 必要时触发冲突或重排判断。

### add_reminder

添加提醒。

例子：

```text
20 分钟后提醒我晾衣服
晚上 9 点提醒我喝药
明天早上提醒我带电脑
```

输出目标：

- 写入 `reminders.jsonl`。

### review_note

记录复盘原因或经验。

例子：

```text
没做完是因为我低估时间了
刚才被临时事情打断了
这个任务以后要先拆大纲
```

输出目标：

- 写入 `reviews.jsonl`。
- 后续可更新 `profiles.json`。

## 解析策略

第一版采用规则优先、AI 兜底。

规则适合处理：

- 明确的开始、暂停、继续、结束工作。
- 常见相对时间，例如“20 分钟后”“明天早上”。
- 明确时间段，例如 `20:00-22:00`。
- 简单提醒。

AI 适合处理：

- 判断一句话属于哪类意图。
- 从自然语言中提取标题、时间、任务类型。
- 把含糊表达改写成结构化候选结果。
- 生成重排建议的表达文本。

冲突判断不交给 AI 做最终决定，由程序根据数据判断。

## 标准解析结果

解析结果先生成一个候选对象，再决定是否写入。

示例：

```json
{
  "intent": "add_task",
  "confidence": 0.86,
  "needsConfirmation": false,
  "rawText": "今晚我要写完产品方案",
  "fields": {
    "title": "写完产品方案",
    "dueAt": "2026-06-01T23:59:00+08:00",
    "estimatedMinutes": null,
    "tags": ["product"]
  },
  "questions": [],
  "warnings": []
}
```

## 需要确认的情况

以下情况不直接写入，进入 `interactionState = confirming`：

- 语音识别文本还没有被用户确认。
- 时间不明确，例如“明天上午开会”。
- 用户表达有多个可能意图。
- 解析置信度低。
- 疑似重复任务或日程。
- 与已有日程或时间块冲突。
- 动态重排会移动已有计划。
- 重要事项缺少关键信息。

确认问题要短，不要像表单审问。

例子：

```text
“明天上午开会”还差具体时间。你想先记成上午待定，还是补一个时间？
```

## 可以直接写入的情况

以下情况可以直接写入：

- 用户输入信息明确。
- 不和已有安排冲突。
- 不是疑似重复。
- 不是会影响已有计划的重排。
- 是低风险生活提醒或简单任务。

例子：

```text
20 分钟后提醒我晾衣服
```

可以直接写入 `reminders.jsonl`。

## 输出到页面状态

输入解析会影响页面状态：

- `start_work`：`sessionState = working`
- `pause_work`：`sessionState = paused`
- `resume_work`：`sessionState = working`
- `finish_work`：可能回到 `idle`，也可能进入 `reviewing`
- 信息不完整或冲突：`interactionState = confirming`
- 添加提醒：通常不改变 `sessionState`

页面状态细节见 `03-page-state.md`。

## 第一版不做

- 不做多轮复杂对话规划。
- 不让 AI 自动移动大量计划。
- 不直接解析语音音频，先依赖浏览器识别成文本。
- 不追求所有自然语言都能一次解析成功。
- 不把 AI 结果直接当最终事实，关键操作仍需程序判断或用户确认。

## 验收标准

- 能区分任务、日程、提醒、工作状态、进度和复盘。
- 明确输入可以直接写入对应数据文件。
- 含糊输入会进入确认流程。
- 工作相关输入能正确影响页面状态。
- 解析结果保留 `rawText`，方便后续复盘和调试。
