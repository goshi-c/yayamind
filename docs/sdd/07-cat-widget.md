# 07 小猫浮窗 SDD

## 目标

小猫浮窗是第一版个人助手的主要情感入口。它要让用户感觉是在和一个轻量陪伴型助手互动，而不是在填写冷冰冰的任务表单。

第一版重点不是精致动画，而是跑通这些核心体验：

- 小猫常驻页面角落。
- 可以点击、拖动、冒气泡。
- 可以打开文字输入。
- 可以触发语音输入并确认识别文本。
- 可以承接提醒、确认、复盘等轻量交互。

## 基础形态

第一版在 Web 页面里模拟桌面浮窗，不做真正系统级桌面能力。

默认位置：

```text
页面右下角或右侧边缘
```

基础元素：

- 小猫主体。
- 气泡提示。
- 输入面板。
- 语音按钮。
- 确认/取消操作。

小猫视觉可以先用简单图形、图片或轻量动画占位，不要求第一版就做复杂动作。

## 基础交互

### 点击

点击小猫时：

- 如果当前没有展开输入面板，打开输入面板。
- 如果有未处理提醒或确认事项，优先展示当前待处理内容。
- 如果当前正在工作，可以展示当前任务的轻量状态。

### 拖动

用户可以拖动小猫到页面边缘或角落。

第一版规则：

- 只需要在当前页面内拖动。
- 不需要记住跨设备位置。
- 可以把最后位置存到 `settings.json`，但不是第一版必须项。

### 气泡

气泡用于短提示，不用于长文本。

适合展示：

- 操作成功反馈。
- 到点提醒。
- 当前工作轻提示。
- 需要确认的简短问题。
- 复盘时的简短追问。

气泡不应该频繁打扰用户，尤其是在 `working` 状态下。

## 输入流程

### 文字输入

用户打开输入面板后，可以输入自然语言。

流程：

```text
用户输入文本
  -> input-parser 解析
  -> 明确且无冲突：直接写入
  -> 不明确或有冲突：进入确认
```

解析规则见 `02-input-parser.md`。

### 语音输入

第一版语音输入使用浏览器能力先识别成文本。

流程：

```text
用户点击语音按钮
  -> 浏览器语音识别
  -> 展示识别文本
  -> 用户确认或修改
  -> 再提交给 input-parser
```

语音识别结果不能绕过用户确认直接写入业务数据。

## 确认流程

小猫浮窗可以承接 `interactionState = confirming` 的确认。

常见确认：

- 语音识别文本确认。
- 时间不明确。
- 疑似重复。
- 时间冲突。
- 重排方案选择。

确认内容要短，避免变成表单。

示例：

```text
这件事和今晚 20:00-22:00 的“写方案”重叠了。要保留原计划，还是把写方案挪到明天上午？
```

## 提醒承接

提醒触发时，小猫可以冒泡轻提示。

规则：

- 工作中不强打断。
- 如果浏览器通知可用，可以同时发通知。
- 用户未处理时，提醒安静进入右侧今日面板。
- 小猫不需要持续追着用户提示。

提醒规则见 `08-reminders.md`。

## 复盘承接

当任务没完成或用户主动复盘时，小猫可以承接复盘问题。

第一版原则：

- 不明显切换人格或氛围。
- 语气比日常更认真一点。
- 重点是问清原因、记录经验。
- 不做批评式、审问式反馈。

复盘产生的数据写入 `reviews.jsonl`。

## 与页面状态的关系

小猫浮窗根据 `03-page-state.md` 的状态调整行为。

- `idle`：轻量陪伴，可提示今日计划。
- `working`：减少打扰，支持记录进度、暂停、结束。
- `paused`：支持继续、结束、记录原因。
- `reviewing`：承接复盘问题。
- `confirming`：展示确认问题或方案。
- `reminding`：冒泡提示提醒。

## 第一版不做

- 不做真正桌面置顶窗口。
- 不做系统托盘。
- 不做全局快捷键。
- 不做开机启动。
- 不做复杂小猫动画。
- 不做自动看屏幕或截图理解。
- 不做多角色人格切换。

## 验收标准

- 页面上有一个可见的小猫入口。
- 小猫可以打开文字输入。
- 语音输入需要先展示识别文本并由用户确认。
- 小猫能承接提醒、确认和复盘问题。
- 工作中提醒不强打断，只做轻提示。
- 未处理提醒能进入右侧今日面板。
- 小猫行为能和页面状态保持一致。
