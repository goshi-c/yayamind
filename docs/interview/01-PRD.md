# YayaMind PRD｜AI 个人助手 Web MVP

## 1. 文档目的

本文是 YayaMind 面向 AI 产品经理面试的产品需求文档。它回答四个问题：

- 为什么要做这个产品；
- 目标用户是谁；
- 第一版做了哪些核心能力；
- 后续如何继续产品化。

YayaMind 当前形态是一个本地优先的 AI 个人助手 Web MVP。它用 Web 工作台模拟未来桌面个人助手：左侧是功能导航，中间是一周日程和项目待办，右侧是日期详情或月历，小猫浮窗承担语音输入、理解确认和陪伴反馈。

## 2. 项目背景

很多学生、求职者和独立学习者并不缺 TODO 工具，而是缺一个能帮助他们把“模糊想法”变成“可执行安排”的助手。

典型问题包括：

- 计划散落在聊天、脑子、Obsidian、日历和 TODO 里；
- 任务说法很口语，例如“明天那个会记得带电脑”“学校新增一个待办，周四要交开题报告”；
- 普通待办只负责记录，不会帮助用户判断冲突、补全缺失信息、追踪执行；
- 日历只展示时间，不理解任务背后的准备事项、提醒和复盘；
- AI 聊天工具能回答问题，但不天然沉淀成本地结构化数据。

YayaMind 的产品假设是：个人效率工具不应该只做“记录容器”，而应该成为一个轻量的执行伙伴。它需要理解自然语言、写入结构化安排、在关键时刻追问、在执行过程中给反馈，并把数据留在用户本地。

## 3. 目标用户

### 核心用户

- 正在准备求职、开题、课程、项目和日常安排的学生；
- 有多个任务线并行、容易忘事、计划经常变化的人；
- 熟悉 Obsidian 或本地文件，希望数据可控、可迁移的用户；
- 希望把 AI 产品设计、前后端实现和本地数据闭环包装成作品集的 AI 产品经理候选人。

### 使用场景

- 早上打开工作台，看今天和本周的安排；
- 通过小猫语音输入一句自然语言，把它写入日程或待办；
- 系统发现时间缺失、冲突或重复时，只追问一个关键问题；
- 写入后自动定位到对应日期和时间，让用户确认系统理解是否正确；
- 在右侧详情里查看具体内容、准备事项、截止任务和提醒；
- 晚上生成 Markdown 总结，沉淀到本地文件或 Obsidian。

## 4. 产品定位

YayaMind 不是普通 TODO，也不是完整商业日历，而是：

> 一个本地优先、语音优先、带陪伴感的 AI 执行助手。

核心差异：

- 用自然语言作为主入口，而不是先让用户填复杂表单；
- 一句话可以生成日程、待办、提醒、准备事项、执行记录；
- 用“确认 / 修改 / 取消”保护写入质量；
- 用本地 JSON/JSONL/Markdown 保存数据，便于作品集展示和后续迁移；
- 用小猫角色降低用户记录任务的心理负担。

## 5. 产品目标

### MVP 目标

- 跑通“自然语言输入 -> 结构化理解 -> 写入本地数据 -> 日程/待办展示 -> 右侧详情编辑”的闭环；
- 证明 AI 可以参与个人日程和任务管理，但不完全依赖 AI；
- 形成可演示、可讲解、可作为 AI PM 作品集的 Web MVP。

### V1.1 目标

- 提升语音输入体验；
- 增强项目待办；
- 打磨日程拖拽、右侧详情、确认卡片和小猫反馈；
- 让产品更像一个真实可用的个人工作台，而不是静态 demo。

## 6. 核心功能需求

### 6.1 一周日程工作台

用户打开页面后默认看到自然周的一周安排。

需求：

- 周一到周日固定 7 列；
- 今天列高亮，过去日期弱化；
- 每天内部有时间轴；
- 时间块按位置和高度表达开始/结束时间；
- 当前时间线实时更新；
- 未来安排入口只展示本周之后有安排的日期。

当前实现：

- 时间轴范围为 7:00-24:00；
- 半小时为一格；
- 日程块支持拖动移动和上下拉伸；
- 冲突日程可并列展示。

### 6.2 项目待办

项目待办用于管理没有精确时间块、但需要完成的任务。

需求：

- 默认三列：工作、学校、生活；
- 新增其他项目后进入“其他项目”分页；
- 每个项目下纵向排列待办；
- 待办支持标题编辑、备注编辑、完成/恢复、删除；
- 待办可拖到月历日期设置 deadline；
- 日期 tag 用马卡龙色阶表达紧急程度。

当前紧急度色阶：

- 今天/过期：最深红；
- 1-2 天：珊瑚粉；
- 3-4 天：桃粉；
- 5-7 天：淡杏；
- 8 天以上：浅灰。

### 6.3 小猫语音输入

小猫是主要输入入口。

需求：

- 点击小猫开始听写；
- 停顿约 1 秒后自动理解；
- 按住并移动才拖动小猫，避免点击和拖动冲突；
- 首屏默认不弹历史气泡；
- 只有听写、思考、追问、确认、修改时显示气泡；
- 语音识别错误可进入纠错流程。

### 6.4 输入理解与确认

系统需要识别用户是在新增、修改、删除还是补充已有事项。

需求：

- 新增日程、待办、提醒、工作记录；
- 修改已有会议时间；
- 给已有会议补充准备事项；
- 删除已有会议；
- 时间不明确时追问；
- 冲突时给少量明确选项。

交互原则：

- 不暴露内部技术逻辑；
- 不把所有字段都展示给用户；
- 只展示“标题 / 具体内容 / 提前准备”等用户能理解的结构；
- 冲突只给“修改 / 重叠 / 取消”等动作。

### 6.5 右侧日期详情

右侧是用户查看和编辑详情的主区域。

需求：

- 展示选中日期完整安排；
- 展示具体事项、时间、准备事项、提醒；
- 支持内联编辑；
- 任务、日程和执行记录可以软删除；
- 待补充事项独立展示，不误放进时间轴。

### 6.6 提醒与天气

需求：

- 支持浏览器通知；
- 支持提醒完成、稍后、忽略；
- 对外出安排结合天气生成出门提醒；
- 默认不写死城市，使用本地配置。

当前实现：

- 后端通过 Open-Meteo 获取天气信号；
- 出门提醒展示在右侧日期详情；
- 普通提醒减少噪音，只保留必要提醒区。

### 6.7 总结与个人画像

需求：

- 记录工作开始、暂停、继续、完成；
- 根据执行记录形成个人画像；
- 生成每日/每周 Markdown 总结；
- 输出到 `personal-assistant-data/summaries/`。

## 7. 核心用户流程

### 流程 A：新增日程

1. 用户点击小猫；
2. 用户说“明天下午三点在软件园开会，提前准备 TODO 和 SDD”；
3. 系统识别时间、地点、类型、准备事项；
4. 如果没有冲突，写入 `events.jsonl`；
5. 页面跳到对应日期时间；
6. 小猫展示确认 / 修改 / 取消。

### 流程 B：新增项目待办

1. 用户说“学校新增一个待办，周四要提交开题报告表格版”；
2. 系统识别项目为“学校”；
3. 标题清理为“提交开题报告表格版”；
4. deadline 写入 `dueAt`；
5. 待办显示在学校列；
6. 日期 tag 按紧急程度变色。

### 流程 C：修改已有会议

1. 用户说“把明天的机器人会议改到下午三点到四点”；
2. 系统先匹配已有会议；
3. 明确这是修改，不是新增；
4. 更新 `events.jsonl` 中对应记录；
5. 页面刷新并定位到新时间。

### 流程 D：生成总结

1. 用户点击总结；
2. 选择生成今日或本周总结；
3. 后端读取 events、tasks、work_logs 等文件；
4. 生成 Markdown；
5. 写入 summaries 目录。

## 8. MVP 范围

已完成：

- React/Vite Web 工作台；
- Fastify 本地 API；
- JSON/JSONL 本地数据层；
- 一周日程视图；
- 项目待办；
- 小猫语音入口；
- AI/规则双通道输入解析；
- 冲突与追问；
- 右侧详情编辑；
- 提醒与天气；
- 总结与个人画像雏形。

暂不做：

- 真正桌面常驻应用；
- 手机 App；
- 多用户账号；
- 云同步；
- 微信入口；
- 系统级屏幕感知；
- 复杂团队协作。

## 9. 成功标准

面向使用：

- 用户可以通过一句话新增日程或待办；
- 写入后能立即在对应视图看到结果；
- 系统不会把修改误判成新增；
- 时间冲突或缺失时能追问；
- 右侧详情能承载完整信息；
- 数据保存在本地文件中。

面向面试：

- 能讲清楚用户痛点和产品定位；
- 能讲清楚 PRD 到 SDD 到代码实现的过程；
- 能展示 AI PM 的需求拆解、MVP 收敛、交互设计和技术理解；
- 能说明当前不足和下一步路线。
